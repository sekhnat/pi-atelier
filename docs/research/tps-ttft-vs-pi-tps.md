# TPS, TTFT, duration, and usage: Pi Atelier vs. pi-tps

## Scope

This note compares Pi Atelier at local commit `567f2c417fd7baef9c09680c7b9582112fcef65b` with [`monotykamary/pi-tps` at `c758d91b31ef1804612145f52fb495465d18297c`](https://github.com/monotykamary/pi-tps/tree/c758d91b31ef1804612145f52fb495465d18297c). Evidence is limited to source, README/specs, and tests in those two repositories.

The headline conclusion is that the two `TPS` values are **not equivalent measurements**. Pi Atelier reports the latest **provider response** using all final output tokens over first-observed-token-to-`message_end` time. pi-tps reports one **whole-turn** value, aggregating assistant messages and applying stream-quality, stall, plausibility, and tool-call gates. Pi Atelier additionally has a separate whole-agent-run duration and session-wide usage aggregate; pi-tps persists per-turn telemetry.

## Window and edge-case details

### Pi Atelier

- **The live numerator is estimated, not streamed token deltas.** Every `message_update` re-tokenizes the full accumulated message, then divides that cumulative estimate by time since the first positive estimate. The first positive estimate establishes TTFT and deliberately emits no TPS ([`extensions/index.ts:916-920`](../../extensions/index.ts#L916-L920), [`src/run-activity.ts:196-221`](../../src/run-activity.ts#L196-L221)). This is responsive, but chunk frequency and tokenizer estimation can move the displayed `~TPS` independently of provider usage.
- **Final TPS is simple and permissive.** A bursty buffered response can produce a very high finite number; an inference pause lowers it because all post-first-token wall time remains in the denominator. Invalid/non-positive final output or a zero-duration window does not produce a new final TPS: it preserves the existing performance value (TTFT-only after the first update, or the last `estimated` TPS after later updates). Updates without an active provider request are ignored ([`src/run-activity.ts:224-236`](../../src/run-activity.ts#L224-L236), [`tests/run-activity.test.ts:76-94`](../../tests/run-activity.test.ts#L76-L94)).
- **Reset boundaries are explicit.** A new provider request clears response performance; a new `agent_start` resets the whole run; session replacement/shutdown disposes and resets the tracker ([`src/run-activity.ts:164-176`](../../src/run-activity.ts#L164-L176), [`:301-315`](../../src/run-activity.ts#L301-L315), [`extensions/index.ts:344-369`](../../extensions/index.ts#L344-L369)). `session_tree` itself only refreshes TODO/render state and does not clear run performance ([`extensions/index.ts:892-897`](../../extensions/index.ts#L892-L897)).
- **Malformed usage is fail-closed per message.** All four token fields must be finite numbers or that message is skipped. Zero prompt totals produce no hit percentage, while finite zero cost is still “available” ([`src/metrics.ts:34-59`](../../src/metrics.ts#L34-L59), [`tests/metrics.test.ts:40-81`](../../tests/metrics.test.ts#L40-L81)).

### pi-tps

- **Stall semantics:** gaps of at least 500 ms between post-TTFT updates count in full; contiguous qualifying gaps form one stall. `message_start` resets only the stall clock ([`index.ts:72-73`](https://github.com/monotykamary/pi-tps/blob/c758d91b31ef1804612145f52fb495465d18297c/extensions/pi-tps/index.ts#L72-L73), [`:678-723`](https://github.com/monotykamary/pi-tps/blob/c758d91b31ef1804612145f52fb495465d18297c/extensions/pi-tps/index.ts#L678-L723)).
- **Reliability gates:** the primary branch requires at least five post-TTFT updates, at least 1 ms average gap, at least 200 ms after subtracting stalls, and stalls shorter than both the stream and active windows. Fallback requires at least two updates and at least 200 ms summed generation time. Values over 10,000 TPS are nulled ([`index.ts:372-391`](https://github.com/monotykamary/pi-tps/blob/c758d91b31ef1804612145f52fb495465d18297c/extensions/pi-tps/index.ts#L372-L391), [`:432-485`](https://github.com/monotykamary/pi-tps/blob/c758d91b31ef1804612145f52fb495465d18297c/extensions/pi-tps/index.ts#L432-L485)). **The pinned README says the fallback threshold is 50 ms**, but the executable constant is 200 ms ([`README.md:158-166`](https://github.com/monotykamary/pi-tps/blob/c758d91b31ef1804612145f52fb495465d18297c/README.md#L158-L166)); use source behavior.
- **Primary-window numerator and denominator do not cover the same interval.** The first update records TTFT and returns; the next update starts `streamMs`, yet the numerator is all output tokens for the turn. The project test intentionally computes 20 tokens over `800 − 400 = 400 ms`, even though the first token arrived at 200 ms and the message ended at 900 ms ([`index.ts:393-446`](https://github.com/monotykamary/pi-tps/blob/c758d91b31ef1804612145f52fb495465d18297c/extensions/pi-tps/index.ts#L393-L446), [`:693-707`](https://github.com/monotykamary/pi-tps/blob/c758d91b31ef1804612145f52fb495465d18297c/extensions/pi-tps/index.ts#L693-L707), [`precision-timing.test.ts:105-121`](https://github.com/monotykamary/pi-tps/blob/c758d91b31ef1804612145f52fb495465d18297c/extensions/pi-tps/__tests__/precision-timing.test.ts#L105-L121)). That is an active-stream heuristic, not a directly interval-matched throughput, and it can read higher than Pi Atelier even without stalls.
- **Multi-message nuance:** `totalGenerationMs` excludes gaps between messages, but `firstStreamUpdateMs`, `lastStreamUpdateMs`, and `updateCount` are turn-global and are not reset at `message_start`. Therefore the primary stream span can cross a tool/message gap even though that gap is not classified as a stall; this conservatively lowers primary TPS. The README's blanket statement that tool gaps are excluded is precise for summed generation/fallback and stall counting, not for the turn-global primary span ([`index.ts:123-131`](https://github.com/monotykamary/pi-tps/blob/c758d91b31ef1804612145f52fb495465d18297c/extensions/pi-tps/index.ts#L123-L131), [`:674-681`](https://github.com/monotykamary/pi-tps/blob/c758d91b31ef1804612145f52fb495465d18297c/extensions/pi-tps/index.ts#L674-L681), [`README.md:132-156`](https://github.com/monotykamary/pi-tps/blob/c758d91b31ef1804612145f52fb495465d18297c/README.md#L132-L156)).
- **Tool-call cap:** per-model maxima are retained in one extension-lifetime `Map`; primary measurements can raise the cap, fallback tool-call values are clamped to it, and a cold-start fallback tool call becomes `null` ([`index.ts:529-535`](https://github.com/monotykamary/pi-tps/blob/c758d91b31ef1804612145f52fb495465d18297c/extensions/pi-tps/index.ts#L529-L535), [`:785-805`](https://github.com/monotykamary/pi-tps/blob/c758d91b31ef1804612145f52fb495465d18297c/extensions/pi-tps/index.ts#L785-L805), [`dynamic-tps-cap.test.ts:121-164`](https://github.com/monotykamary/pi-tps/blob/c758d91b31ef1804612145f52fb495465d18297c/extensions/pi-tps/__tests__/dynamic-tps-cap.test.ts#L121-L164)). Session start/tree handlers do not clear that map. Turn timing is replaced on every `turn_start` and nulled on `turn_end`; branch navigation clears cost-correction bookkeeping and restores the latest branch notification ([`index.ts:624-663`](https://github.com/monotykamary/pi-tps/blob/c758d91b31ef1804612145f52fb495465d18297c/extensions/pi-tps/index.ts#L624-L663), [`:757-763`](https://github.com/monotykamary/pi-tps/blob/c758d91b31ef1804612145f52fb495465d18297c/extensions/pi-tps/index.ts#L757-L763)).
- **Input validation differs.** An assistant message is accepted when `usage.input` and `usage.output` merely have type `number`; finiteness is not checked, and cache/total fields default through `|| 0` ([`index.ts:187-195`](https://github.com/monotykamary/pi-tps/blob/c758d91b31ef1804612145f52fb495465d18297c/extensions/pi-tps/index.ts#L187-L195), [`:329-340`](https://github.com/monotykamary/pi-tps/blob/c758d91b31ef1804612145f52fb495465d18297c/extensions/pi-tps/index.ts#L329-L340)). Zero output, missing first token, or missing model suppresses the telemetry entry entirely ([`index.ts:348-350`](https://github.com/monotykamary/pi-tps/blob/c758d91b31ef1804612145f52fb495465d18297c/extensions/pi-tps/index.ts#L348-L350)).

## Formatting

- Pi Atelier renders `TTFT` as integer milliseconds below one second and one-decimal seconds thereafter; TPS is one decimal, `~` means estimated, and `~` alone means unavailable. Its run duration floors to whole seconds (`<1s`, `12s`, `1m 08s`, `1h 02m`) ([`src/run-activity.ts:75-120`](../../src/run-activity.ts#L75-L120), [`tests/run-activity.test.ts:312-323`](../../tests/run-activity.test.ts#L312-L323)). Footer usage uses lowercase `k`, rounded thousands above 10k, and `M`; the sidebar instead keeps one decimal and extends through `B` ([`src/metrics.ts:80-86`](../../src/metrics.ts#L80-L86), [`src/sidebar.ts:446-452`](../../src/sidebar.ts#L446-L452)).
- pi-tps renders `TPS 42.5 tok/s` or `TPS —`, TTFT and total duration in the same duration formatter, token counts with uppercase `K/M/B`, optional stall count, and optional blended `$/M` ([`index.ts:198-234`](https://github.com/monotykamary/pi-tps/blob/c758d91b31ef1804612145f52fb495465d18297c/extensions/pi-tps/index.ts#L198-L234), [`:285-305`](https://github.com/monotykamary/pi-tps/blob/c758d91b31ef1804612145f52fb495465d18297c/extensions/pi-tps/index.ts#L285-L305)). Sub-minute durations always show one decimal; longer durations show up to two units through years ([`format-duration.test.ts:9-81`](https://github.com/monotykamary/pi-tps/blob/c758d91b31ef1804612145f52fb495465d18297c/extensions/pi-tps/__tests__/format-duration.test.ts#L9-L81)).

## Practical recommendations

1. **Do not present the values as interchangeable.** Document Pi Atelier as **latest-response TPS/TTFT** and its duration as **agent-run wall time**. pi-tps is a **turn aggregate** with conditional denominator selection.
2. **Adopt `performance.now()` for response and run elapsed time.** It avoids wall-clock adjustments and preserves sub-millisecond windows while leaving `Date.now()` for persisted timestamps.
3. **Keep the live estimate, but expose provenance.** Preserve the useful `~` marker and consider naming the fields `responseTpsEstimate`/`responseTpsFinal`; include response/turn scope if metrics become an API.
4. **Choose an explicit reliability policy before borrowing pi-tps math.** At minimum test buffered bursts, long inter-chunk stalls, very short outputs, and clock rollback. Keep numerator and denominator on the same interval unless the metric is explicitly labeled as a heuristic; do not copy pi-tps's full-turn output over a narrower post-second-update window by default. If adding gates, encode constants once and test/document the same values; pi-tps's 50 ms prose vs. 200 ms code drift is the failure mode to avoid.
5. **Do not silently aggregate Pi Atelier TPS across tool chains.** A valid turn-level metric needs segmented message windows; a single first-to-last span can include tool gaps. Persist per-response components first, then define a weighted aggregation explicitly.
6. **Retain Pi Atelier's stricter usage validation and cache denominator.** If telemetry is exported, include both per-response provider usage and the existing session aggregate; label whether session means `getEntries()` (all entries) or current branch.
7. **Add lifecycle tests around session-tree navigation and replacement.** Decide whether last response performance should survive `/tree`; today Pi Atelier leaves it in place while pi-tps restores the selected branch's persisted last turn and retains model caps across branch/session events.
